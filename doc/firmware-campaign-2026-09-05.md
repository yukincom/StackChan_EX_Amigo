# firmware 改修キャンペーン：夜間表情と会話への参加・静聴

2026-09-05 の追加要件。実装は作業ブランチで進行中。項目別の実装・検証状況は[改修マイルストーン](firmware-milestones-2026-09-05.md)を参照。未フラッシュで、常時録音や外部サービスへの音声送信は開始していない。

## 今回の要件

- 旧版にあった「夜間だけ待機表情が Sleepy」を復活する。
- 毎回タッチやウェイクワードを要求せず、常時マイク待受から自然に会話できるようにしたい。
- 人間同士の会話が盛り上がったら「僕はしばらく静かにしてるね！」と一度伝えて静かにする。
- 登録されている名前で呼ばれたら再び応答し、人間同士の会話が続けばまた静かにする。
- 顔タッチによる会話開始は必ず残す。静聴中も顔タッチで会話参加へ戻れるようにする。
- 本体API認証、音声取得先の制限、HTTPS証明書検証の追加は今回の対象外。既存の保護を削除・無効化するという意味ではない。
- Avatar描画ライブラリ自体の最適化は今回の対象外。口パクは既存APIへ渡す音量・開口率・更新頻度を対象とし、描画エンジンの改造とは分ける。

## 作業の分離とフラッシュの判断

本体ファームは EX Amigo 一本。公開版 `server/` と家庭用 `yuno-chan-api` は二つのサーバーであり、家庭用の別ファームを新設しない。

- **本体用ワークツリー**: 口パク、同期処理とwatchdog、夜間の待機表情、常時マイクの切替と入出力管理、撮影modeの引継ぎを担当する。電源診断の追加は撤回し、既存の電池表示を維持する。
- **対話強化用ワークツリー**: 公開版と家庭用の両方に、会話の参加・静聴判断と、その評価・改善の仕組みを反映する。家族固有の設定・記憶・録音・会話・評価データは非公開側に留め、公開テストには合成ケースだけを使う。
- 分岐元には実機なし保守基盤を含む既存の作業版を使う。家庭用の実運用フォルダにある未コミット変更は移動・破棄・一括commitしない。実験用ワークツリーと実運用を分ける。
- 両作業の境界は音声入力、顔タッチ、再生の状態・停止、録音モードの受渡し。会話参加の意味判断を本体へ焼き込まない。通信仕様を変更する際は両側で整合を確認する。

本体側の検証は既存の実機なし保守ラボ、host上で実行できるロジックのテスト、対象機種のbuildを先に行う。ラボはHTTP契約を再現するものであり、実際のI2S・マイク・描画・電源まで検証したとは扱わない。

自動フラッシュは行わない。まとまった変更について必要なテストとbuildが通り、機種・現行版・戻せるファーム・短い実機確認手順が揃った段階で、ユーザーへフラッシュを依頼する。変更一覧、検証済み範囲、実機でしか判断できない点、復旧方法を一緒に示す。小変更のたびに依頼せず、継続診断のために本体Flashへ頻繁に書き込む設計も避ける。

## 夜間の待機表情：元実装を確認済み

元実装は yuno の Python 側ではなく、関連旧ファーム `dev-m5stack-push-avatar/src/face_service.cpp` の `setFaceExpression(FACE_IDLE)` にあった。

- 19:00 以上、または 00:00〜06:59：`Expression::Sleepy`。
- 07:00〜18:59、または時刻未取得：`Expression::Neutral`。
- 旧版は server から受け取った `serverHour` を利用していた。
- 録音・思考・再生中はそれぞれの表情を使い、待機に戻るときに時間帯の表情へ戻す。

Amigo は `main.cpp` に JST の NTP 設定を持つため、旧 `/notify/pending` 通信を再導入せず、既存の時計を利用する案を優先する。夜間表情は見た目の設定であり、deep sleep、マイクOFF、LINE通知停止とは分離する。

復活時には、会話・通知・撮影・エラー後の待機復帰と、19時/7時をまたぐ待機中の更新を確認する。処理中の表情や明示的に指定された表情を、周期処理が上書きしないようにする。

## 常時マイク：録音と応答の判断を分ける

要求されているのはウェイクワードを毎ターン改善する仕組みではなく、「聞ける状態を保ちつつ、返事をする場面を選ぶ」仕組み。

| 会話状態 | 入力 | 振る舞い |
| --- | --- | --- |
| 会話参加 | スタックちゃんへの発話 | 普通に応答する。毎回名前を要求しない。 |
| 会話参加 | 人間同士のやり取りが続いているという判断 | 会話の切れ目で一度だけ静聴に移る旨を伝える。 |
| 静聴 | 周囲の雑談 | 音声を認識しても応答を生成しない。 |
| 静聴 | 登録名での呼びかけ、または顔タッチ | 会話参加へ戻る。 |

実装上の判断案（まだ有効化していない）:

- 「登録名」はスタックちゃん自身の名前・呼び名を想定する。家族の登録名ではない。`ASSISTANT_NAME` と既存の呼び名設定の対応は実装前に揃える。
- 呼びかけは一般の文字起こし結果から判定し、不調な SimpleVox の音型照合だけに依存しない。第三者として名前を話題にしただけの発話との区別は評価項目にする。
- VAD（声がある区間の検出）や音量だけで「人間同士が盛り上がっている」と決めない。発話内容、呼びかけ、会話の流れを短い一時コンテキストで判断する。判定精度は未検証。
- 静聴移行の一言は状態の切替時に一度だけ。再開直後に同じ一言を連発しないようにする。
- 周囲の会話はローカル処理を基本とし、通常の会話履歴・要約・学習・本文ログに混ぜない。外部AIへ自動転送しない。現在の文字起こし/Serialログをそのまま常時待受へ流用しない。
- 「静聴」はマイクOFFではない。完全なマイクOFF操作は別に残す。静聴中の通知・アラームの扱いは通常会話への応答と分ける。
- 自分の再生音を聞いて再反応するループを防ぐ。初版では再生中/カメラ占有中だけ録音を止める案があるが、これは完全な同時録音・再生ではなく、発話中の割込み受付とも別の仕様になる。

## 既存資産と先に確認する点

- 現 `handle_text_wakeword()` は `robot->listen()` の文字起こし結果から登録語を探す。`AudioWhisper` は 60,000 sample / 16 kHz、約3.75秒の固定録音で、その後にHTTP転送・認識を行う。録音→転送→応答の単純反復では、常時待受には聞き逃す区間が残る。
- 旧関連ファームの `mic_service.cpp` には、音量検出・発話前バッファ・無音終端・再生/撮影中の録音停止が既にある。再利用の参考にするが、旧コードを丸ごと移植して競合が解消するとは扱わない。
- yuno の旧 `STACK_SESSION_MODE_PLAN.md` には `I2S: register I2S object to platform failed` と、Mic/Speaker/Cameraの競合を理由に常時音声起動を見送った記録がある。これは過去の記録であり、現在の実機で再現確認した事実ではない。今回の希望を優先しつつ、録音デバイスの所有・開始停止を整理する。
- 音声区間検出は既存 SimpleVox のVAD、文字起こしは既存 whisper.cpp の再利用をまず検討し、同等機能を一から作らない。人間同士の会話判定はVADとは別の機能。
- ライセンス確認：SimpleVox本体はMIT。ただし同梱 `ThirdPartyNotices.md` に esp-dsp のApache-2.0と、Espressif製品上での利用条件を持つESP-SRのESPRESSIF MITがある。Macへそのまま移植できる一般MITコードとは扱わない。[SimpleVox](https://github.com/MechaUma/SimpleVox)
- whisper.cpp はMIT。[公式LICENSE](https://github.com/ggml-org/whisper.cpp/blob/master/LICENSE)。この調査では新しい依存・モデルを導入していない。

## 改修・検証の順序案

1. 夜間の待機表情を小さく復活し、時刻境界・時刻未取得・動作中表情の保護を実機なしで確認。
2. マイク、再生、カメラの所有と停止/復帰を整理し、従来のタッチ操作を維持する。
3. 合成した発話列で「会話参加→静聴→名前または顔タッチで復帰」を検証。顔タッチでの通常の会話開始、雑談を履歴へ入れないこと、自分の声で起動しないこと、離席の一言を連発しないことも確認。
4. 実機の機種と書込み済み版を確認し、実機向けbuildと短い録音/再生/撮影テストをまとめて行う。常時待受の実際の精度、I2S、負荷、電源は仮想テストだけで完了扱いにしない。

撮影modeの引き継ぎ不足は引き続き既知の別課題。[実機なし保守ラボ](../docs/no-device-lab.md#現在固定している既知差分)を参照。8月の修正済み項目と実機確認待ちは[前回レビュー](cpp-maintenance-review-2026-08-13.md)に残し、未実装項目と混同しない。
