## 結論（後方互換の残り）

**運用CLIの Python 実装への runtime fallback は残っていません。**  
`tools/stackchanctl.py` は未ビルド時に失敗して終了し、旧実装へ戻しません。certifi / uv / pip の旧版継続も fail-closed で、無効化用の環境変数もありません。

残っているのは次の区別が必要です。

| 種別 | 判定 |
|------|------|
| Python shim（exec のみ） | 意図した入口互換。実装本体ではない |
| `tests/fixtures/stackchanctl_python_reference.py` | **実行可能な旧CLIの完全コピー**。テスト専用と明記されているが、実体としては最大の「後方互換残り」 |
| `preflight` → Python doctor | 境界として文書化済み。アプリ診断の意図的な依存 |
| 旧 `/health` | 既存 client 互換。今回の Rust/CA 作業とは別軸 |
| サーバ本体（Flask / MLX / Kokoro 等） | 引き続き Python。CLI 置換の範囲外 |

「堅牢性のために Rust へ置き換えた」対象は **運用CLI（status / run-server の HTTP・uv 検査・exec）** であり、アプリ全体の Rust 化ではない、という境界はドキュメントと実装で一致しています。

## うまくできている点

1. **Fail closed**  
   Native binary なし → exit 1。古い certifi / uv / pip → `RuntimeError`。TLS 検証無効化や「検査スキップ」フラグなし。

2. **意味の重なる第二経路を増やしていない**  
   Pytra 変換は不採用。手書き Rust に一本化。`STACKCHANCTL_BIN` はビルド先の指定であり、Python 実装への逃げ道ではない。

3. **境界変更が明示されている**  
   proxy / redirect 不使用、空 query/fragment 拒否、不正 port を 80 に落とさない補正。旧 Python より狭い攻撃面。

4. **比較テストの置き方**  
   旧版を `tests/fixtures/` に固定し、native と exit code / JSON を突き合わせる。`test_missing_native_binary_fails_without_fallback` で shim の非 fallback を固定している。

5. **CA 対応と CLI 置換の分離**  
   `security_runtime` は Python ランタイム側。Rust CLI は loopback 平文 HTTP のみで CA bundle を持たない、という切り分けが文書どおり。

6. **doctor の役割分担**  
   更新前環境でも offline 診断は動かし、不足版を結果へ出す。サーバ起動とは別経路。ここは「旧環境でサーバを動かし続ける互換」ではない。

## 後方互換・残骸の詳細

### 1. 実行可能な Python 参照実装（要注目）

`tests/fixtures/stackchanctl_python_reference.py` は docstring 上「Test-only / never a runtime fallback」だが、`argparse` + `urlopen` + `os.execvpe` を持つ **単独起動可能な CLI** である。

- uv 下限は `security_runtime.MINIMUM_UV` を参照しており、旧CA対策前の緩い版ではない。
- 一方、Rust 側で意図的に切った proxy / redirect 拒否は、この参照実装では urllib の既定挙動に近い。差分テストでも redirect ケースは native のみ検証。
- 運用パスから import されていないことは確認した。リスクは「発見して直接実行する」運用ミス。

**推奨:** 入口に「テスト専用・運用禁止」を stderr か assert で強調するか、`if __name__` をテスト runner 経由に限定する。長期的には golden JSON / 契約テストへ寄せて実行可能コピーを薄くする。

### 2. ドキュメントの命名残り

`docs/local-service-operations.md` の launchd 節:

> 置換後は `plutil -lint` と `stackchanctl.py ... --dry-run` で検査できます。

shim 経由なら動くが、同ドキュメント前半は `native/.../stackchanctl` を主経路としている。**手順表記の残骸**。`stackchanctl`（または明示の release binary / shim）に揃えると迷いが減る。

### 3. 意図して残している入口（問題なし、ただし寿命を決める）

- `python3 tools/stackchanctl.py …` → `os.execve` のみ。実装ロジックなし。
- launchd 例は `__STACKCHANCTL__`（ビルド済み binary）を指す。Python を挟まない。
- `STACKCHAN_PYTHON` は `preflight` の doctor 用。status / run-server の本体ロジックには使わない。

shim をいつまで残すかをドキュメントに一文あると、将来の「互換削除」判断がしやすい。

### 4. 今回の範囲外で「legacy」と書かれているもの

firmware の legacy touch / wakeword、camera upload v2 と `--legacy-camera-upload`、`openai_compat_routes`、旧 `/health`、voice 配送の legacy `delay_ms` 読み取りなどは、**今回の Python→Rust / eMudhra 作業の後方互換残りではない**。別トラックの互換契約。

### 5. サーバが Python のままであること

Flask・SDK・MLX・Kokoro は Python。これは欠陥ではなく設計境界。堅牢化の対象は「ローカル運用CLIとパッケージ版ゲート」に限定されている。記事の CA 問題への直接対応は `certifi>=2026.10.19` / `uv>=0.13.4` / bootstrap の hash pin 側。

## 小さな観察（後方互換以外）

- `config.py` / `app.py` の双方で `require_secure_environment()` が走り得る（二重呼び出しは冪等で実害は小さい）。
- `STACKCHAN_SKIP_DOTENV` は dotenv 読み込み専用で、CA 検査をバイパスしない（良い）。
- Windows 実行・実サーバ切替・hardware は未検証、と既存記録どおり。
- 関連ツリー `yuno-chan-api` / `yuno-chan-api-update` にも `native/stackchanctl` がある。本レビューの正本は `StackChan_EX_Amigo` の `origin/main`。日々の driver 側への取り込み差分は別確認が必要。

## 総合判定

| 観点 | 判定 |
|------|------|
| 旧 Python CLI への runtime fallback | **なし（良い）** |
| 旧 CA / 旧 uv の黙認継続 | **なし（良い）** |
| テスト用の実行可能旧実装 | **あり（最大の残骸。意図的だが運用に漏れうる）** |
| ドキュメントの旧名称 | **軽微な残り** |
| 意図した互換入口（shim / doctor / `/health`） | **文書化済み。問題視するなら寿命方針だけ足す** |

**後方互換が「残っていないか」への答え:**  
本番運用経路には、旧実装へ戻る逃げ道は残っていない。残っているのは (1) テスト用の完全な Python 参照CLI、(2) exec 専用 shim、(3) 文書上の `stackchanctl.py` 表記、の三点。優先して手を入れるなら (1) の誤用防止と (2)(3) の表記統一。
